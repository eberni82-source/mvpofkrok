# Серверный пилот Cursor

Актуальная серверная реализация и последняя палитра описаны в [документе 09](09_Рабочий_backend_и_палитра.md). Ниже сохранён контекст предыдущих итераций.

Статус: предложение для согласования с командой. Сервер, база, вход и админка ещё не реализованы. Эта ветка остаётся статическим MVP с вымышленными данными и browser-local хранением. Удаление плашки «локальный прототип» не меняет границы хранения и доступа.

## Предлагаемый стек

FastAPI на Python, PostgreSQL, SQLAlchemy и миграции Alembic. Это продолжает стек исходного питча. FastAPI даёт типизированные контракты и OpenAPI, PostgreSQL подходит для связанных сущностей и транзакционной записи встречи, оценок и истории. Redis и отдельная графовая база для первого пилота не требуются. Фронтенд читает API через замену адаптера данных, без доступа к базе из браузера.

Размещение: фронтенд и API за HTTPS на одном домене, API доступен через `/api`. База находится в закрытой сети. GitHub Pages подходит только для статического демо: Python-сервер и PostgreSQL размещаются отдельно. Конкретную инфраструктуру, место хранения и резервирования согласует заказчик до загрузки настоящих данных.

## Как работает доступ

1. Для внутреннего пилота администратор приглашает участника и назначает доступ к клиентам. Открытая регистрация не нужна.
2. При доступном провайдере КРОК пользователь входит через корпоративный SSO по OIDC. При отсутствии провайдера выбрать готовый сервис идентификации для пилота, согласовав условия хранения. Самописный парольный вход не входит в первый этап.
3. Сервер завершает вход, создаёт серверную сессию и устанавливает защищённую cookie `HttpOnly; Secure; SameSite`. Секреты и долгоживущие токены не хранятся в localStorage.
4. Каждый запрос проверяет сессию, организацию, доступ к выбранному клиенту и разрешённое действие. Идентификатор клиента, роль и автор записи из тела запроса не считаются доказательством доступа.
5. Выход отзывает сессию. Исключение участника отбирает доступ при следующем запросе. Срок действия и правила повторного входа задаются политикой пилота.

| Возможность | Читатель | Редактор | Администратор |
| --- | --- | --- | --- |
| Просмотр назначенных клиентов | Да | Да | Да |
| Изменение контактов и связей | Нет | В назначенных клиентах | В назначенных клиентах |
| Запись встречи и оценки | Нет | Да | Да |
| Экспорт | Отдельное разрешение | Отдельное разрешение | Отдельное разрешение |
| Приглашения и права | Нет | Нет | В своей организации |
| Просмотр журнала доступа | Нет | Нет | В своей организации |

Администратор не получает автоматически доступ ко всем организациям. Любой новый API закрыт по умолчанию. Сервер проверяет доступ и на чтение, и на изменение, и на экспорт. Кнопка, скрытая в интерфейсе, не является защитой.

## Минимальная админка

Раздел управления пользователями: приглашение, отзыв приглашения, блокировка, назначение роли и клиентов. Второй раздел: журнал изменений и операций экспорта. Настройки справочников ролей добавляются при необходимости. Отдельный конструктор админки и универсальная CMS пока не нужны.

## Модель базы

| Сущность | Основные поля и ограничения |
| --- | --- |
| organizations | id, name |
| users | id, external_subject, статус; уникальный идентификатор провайдера |
| memberships | organization_id, user_id, role; уникальная пара |
| client_access | membership_id, client_id, can_edit, can_export |
| clients | id, organization_id, name |
| departments | id, client_id, name |
| contacts | id, client_id, department_id, name, position, revision |
| deals | id, client_id, name, stage, next_step |
| deal_participants | deal_id, contact_id, decision_role, influence; роль привязана к сделке |
| relations | id, client_id, deal_id?, source_id, target_id, kind, basis; запрет связи с собой |
| interactions | id, client_id, author_id, date, summary, created_at |
| interaction_participants | interaction_id, contact_id |
| observations | contact_id, deal_id?, field, value, author_id, source_id, observed_at |
| internal_connections | contact_id, user_id; кто знаком с контактом |
| audit_log | actor_id, organization_id, action, entity_id, timestamp, revision |

Связи между клиентами запрещаются составными внешними ключами и серверной валидацией. Дубликаты связей и участников запрещаются уникальными ограничениями. Сохранение встречи, участников, ответов и аудита проходит в одной транзакции. Редактирование использует revision/ETag; устаревшая правка возвращает 409 с предложением перечитать данные. Мнения сотрудников сохраняются отдельно, без усреднения.

## Контракты первого этапа

`GET /api/me` — сессия и права. `GET /api/clients` — только доступные клиенты. `GET /api/clients/{id}/map?deal_id=…` — карта. `PATCH /api/contacts/{id}` — правка с revision. `POST /api/interactions` — встреча и ответы. `POST /api/relations` — связь с основанием. `GET /api/clients/{id}/export` — проверяемое и журналируемое скачивание. `POST /api/invitations`, `PATCH /api/memberships/{id}` — администрирование.

## Безопасность и обязательная приёмка

Серверная валидация схем, ограничение размеров и частоты запросов, параметризованные запросы, проверка CSRF для cookie-сессии, фиксированный список CORS, проверка issuer/audience/state/nonce в OIDC. Автор ответа берётся из сессии. Журналы не содержат паролей, токенов и полного содержимого клиентской переписки. Резервные копии проверяются восстановлением; сроки хранения и удаление согласуются с заказчиком.

Перед реальным пилотом: тесты запрета доступа без сессии, доступа читателя на запись, доступа к чужому клиенту и чужой организации по подменённому ID, просроченной сессии, отозванных прав, повторного приглашения, CSRF, массового экспорта и конфликтующих правок. Положительные сценарии проверяются вместе с отказами. PostgreSQL RLS можно добавить вторым уровнем изоляции; это не заменяет серверную авторизацию и требует отдельного тестирования под рабочей ролью базы.

## Порядок реализации

Сначала согласовать размещение и провайдера входа. Затем схема базы и миграции, сессия и доступ, CRUD карты и транзакционная запись встречи, адаптер фронтенда, минимальная админка, аудит и восстановление из резервной копии. После этого — многопользовательский пилот на разрешённых данных. Текущие E2E фронтенда не доказывают безопасность будущего API.
